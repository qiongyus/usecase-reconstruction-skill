# granularity.md — 用例粒度判据

头号失败模式是粒度失控，且是**双向**的：模型既会把用例切得太碎（界面动作冒充用例），也会把用例并得太粗（多个不相关操作压成一个）。本文给出可操作的判据、正反例与选 `level` 的界线。条款原文与 shall/should 区分见 `content-items.md`，本文不重复引用，只给判据本身。

## 一、完整性判据的操作化（UML §18.1.3.1）

UML 给出的判据是：

> 执行完毕后，subject 是否处于「无待续输入或动作、用例可被重新发起」的状态，或错误态？

把它变成可以对每个候选逐条走一遍的流程：

1. **定位候选对应的入口点**：HTTP 路由、CLI 子命令、消息处理器、定时任务——它是 Step 3（系统操作清单）里的哪一条或哪几条。
2. **追踪该路径直到状态稳定的那一点**：事务是否已提交或回滚完成？响应是否已返回调用方？有没有后续步骤是"同一序列里必须紧接着做的下一步"？
3. **判定**：
   - 稳定点处 subject **不再依赖同一序列的下一步**才算完成（响应已返回、事务已提交或已回滚、无待续状态）→ 通过完整性判据，是候选用例。
   - 到达错误态并已妥善处理（返回错误、事务已回滚）→ 同样通过，"错误状态"是 UML 明文承认的合法终态。
   - 停在半途——必须紧接着执行序列里的另一步才有意义（如"校验完 token 之后还得用它去调用下一个接口，脱离这个上下文校验本身没有独立价值"）→ 判定为片段（`level: subfunction`），不是独立用例。
4. **写下判定理由**，填入 manifest `use_cases[].completeness_check`——不是打勾了事，要写清楚"稳定点是什么、为什么在那里状态已完整"。`goal_confidence` 与这条判据无关，判据是结构性的（可从代码路径判断），置信度约束的是"这条用例对 actor 有什么价值"这类目标层断言。

这条判据只解决"这一个候选够不够格独立成用例"，不解决"两个都够格的候选要不要合并"——那是第四节的辅助判据。

### 对照例：一次 HTTP 请求的完整性判定

以 `DELETE /orders/{id}` 为例走一遍流程：

1. 入口点：路由表里的 `DELETE /orders/{id}` 处理函数。
2. 追踪路径：处理函数校验权限 → 查订单是否存在 → 若存在则标记取消、释放库存、发出取消事件 → 返回 204；若不存在返回 404。两条分支都在处理函数返回时结束，没有"必须紧接着做下一步才有意义"的后续动作。
3. 判定：两条分支到达时 subject（订单子系统）都不再有待续输入——成功分支是稳定的新状态，失败分支是 UML 承认的错误态——**通过完整性判据**，`Cancel Order` 是候选用例，`variant: normal` 对应成功分支，`variant: exception` 对应 404 分支。
4. 反例对照：处理函数内部单独抽出来的"校验权限"一步，脱离这次取消请求没有独立价值，不通过判据，是 `Cancel Order` 内部的一个步骤，不是独立用例（也不必然要单独建一个 `subfunction` 条目，见第五节）。

### 已知边界情况：异步与长时任务

同步请求-响应结构的判定最容易走完流程。异步场景更难判——例如"提交批处理任务"后立即返回一个任务 ID，真正的处理在后台异步完成。这里"无待续输入"在**提交这一步**已经成立（调用方拿到任务 ID 后可以走开，subject 处于"任务已排队"的稳定态），所以`Submit Batch Job` 通常仍能独立通过判据；而"后台任务本身如何处理"是否要另建一个用例，取决于是否存在独立的 actor（例如系统自身的调度器）以及是否有独立的可观察结果（如完成通知）。这类候选判起来更依赖具体代码证据，判定理由要写得比同步例子更详细——这正是 `completeness_check` 要求写出"理由"而不只是布尔值的原因。

## 二、双向失控的识别：先看实证

UCRBench（arXiv:2512.13360，*UCRBench: Benchmarking LLMs on Use Case Recovery*）在 9 个真实项目上构造了人工校验的用例基准，其中 Xpipe 项目（Remote Infrastructure Management，66,609 行）人工标注了 **37 个子功能（subfunction）用例**；同一项目上，GPT-5 生成了 **2103 个子功能用例**（约 57 倍），产出「Check GPU」「Show loading」这类界面动作——这些是实现细节或 UI 反馈，脱离上下文没有独立价值，本该在第一节的判据下被并入更大的用例。

反方向同样失控：在 Rouyi 项目的 user-goal 级重建中，GPT-5 把 **19 个子功能用例合并成 1 个** user-goal 用例——过度抽象，丢失了本该分开报告的差异化行为。

| 方向 | 项目 | 人工基准 | 模型产出 | 表现 |
|---|---|---|---|---|
| 过细（切碎） | Xpipe（subfunction 级） | 37 个 | GPT-5：2103 个 | 约 57 倍，含 `Check GPU`、`Show loading` 等界面动作 |
| 过粗（合并） | Rouyi（user-goal 级） | —（19 个应分立的子功能） | GPT-5：合并为 1 个 | 差异化行为被压扁，丢失可追溯性 |

两个方向的病因相同：**没有对"是否完整"做显式判定，而是凭表面模式（函数名像动词就当用例 / 数量太多就合并）决定粒度。**

> **此处引用的是失败模式的结构性描述，不是分数基线。** 该论文评测的模型（GPT-5、GPT-5-mini、DeepSeek-V3.2-Chat/Reasoner）已非当前最新一代，其 AccA / AccN / OR 等具体分数对当前模型的参考价值存疑，**不作为本 skill 的准确率目标或基线**。真正可移植、不随模型升级自动失效的结论是论文原句：
>
> > "current models lack **explicit mechanisms for regulating abstraction levels or reasoning hierarchies**. Future work could explore structured prompting or code-guided decomposition methods to achieve more stable granularity control."（论文 §5 Discussion）
>
> 即：这是**机制缺失**，不是能力不足——模型没有一把可复用的粒度尺，所以第一节的完整性判据必须由本 skill 显式提供，而不是指望模型自行掌握分寸。

### 对治不是"提醒模型注意粒度"，是改变生成顺序

论文点名的补救方向——"structured prompting or **code-guided decomposition**"——不是空话，本 skill 的工作流本就按这个方向设计：先机械列出全部对外操作（系统操作清单，事实层），再用第一节的判据把操作**聚合**成用例（假说层），而不是让模型直接对着代码"想"出一份用例清单。**操作清单必须先于聚合产出**——顺序颠倒是失控的直接原因：先想用例名再找证据，判据就成了事后合理化，而不是真正的筛选。Xpipe 的 2103 个「Check GPU」类条目，本质是把操作清单本身当成了用例清单，跳过了聚合这一步。

## 三、正反例

### 反例（5 组，覆盖 brief 指定的五类失控）

| 候选名 | 判定 | 理由 |
|---|---|---|
| `Get User Profile`（作为独立用例） | ✗ 过细 | getter 类：查询后 subject 状态不变，通常是另一个用例内部的一步（如"查看个人主页"里的一次读取），不满足"对 actor 独立可观察的价值" |
| `Show Loading` | ✗ 过细 | UI 动作类：纯界面反馈，不涉及 subject 的状态迁移，是 UCRBench 里 GPT-5 在 Xpipe 上过度生成的典型例子 |
| `Validate Token` | ✗ 过细 | 内部步骤类：校验通过后系统仍处于"待续"状态（还要用这个 token 去做别的事），脱离所属用例上下文没有独立价值，不通过完整性判据 |
| `Manage Data`（把 ingest 与 query 合并） | ✗ 过粗 | 过度合并类：ingest 与 query 是两条互不依赖、可独立发起、独立产出价值的路径，硬并成一个用例会掩盖它们各自的场景与失败模式，属于"为了少写几个用例"的错误合并，不是 REQ-N04 意义上的 CRUD 合并 |
| `Create User` / `Update User` / `Delete User` / `List User`（各自独立成用例，未合并） | ✗ 过细 | CRUD 未合并类：四个分立目标应按 REQ-N04【二手，Cockburn】合并为一个 `Manage Users`，逐个单列会让用例清单虚高，且它们描述的是同一资源生命周期的不同侧面，不是彼此独立的用户目标（见 `REQ-N04`） |

### 正例（5 组）

| 候选名 | 判定 | 理由 |
|---|---|---|
| `Register Account` | ✓ | 账户创建落库并返回结果（成功或校验失败）后，subject 无待续输入，可重新发起 —— 通过完整性判据 |
| `Authenticate User` | ✓ | 认证结果（通过/拒绝）返回后即为完整终态，即使被拒绝也是"错误态"意义上的合法完成 |
| `Process Payment` | ✓ | 支付流程完成（成功记账）或失败回滚后 subject 均处于稳定状态，二者都是独立可观察、对 actor 有价值的结果 |
| `Export Report` | ✓ | 报表生成并可下载后即完成，不依赖后续步骤；即便涉及多个内部子步骤，对外只有一个完整使用单元 |
| `Manage Users`（CRUD 合并后的正确形态） | ✓ | 创建/查询/修改/删除四个分立目标按 REQ-N04 塌缩为一个用例，与反例表最后一行对照：正确答案不是四个用例，是合并后的这一个 |

## 四、辅助判据：`no_association_to_use_case` 的语义根据

第一节的判据回答"这一个候选够不够格"，但两个各自都够格的候选仍可能其实是一个用例硬拆出来的两半。UML §18.2.5.6 的 `no_association_to_use_case` 约束禁止同一 subject 的用例之间建立关联，其语义根据在 §18.1.3.1：

> 每个用例各自 "describes a **complete usage** of the subject"。

反过来读：**若两个候选用例必须连着做才有意义——一个不做，另一个单独做没有价值——它们就不是两个互相关联的用例，而是一个用例。** 这是判断"要不要合并"的判据，和第一节判断"要不要拆分"的判据互补：

- 完整性判据（第一节）筛掉**太碎**的候选——判断单个候选是否已经是一次完整使用。
- 关联判据（本节）筛掉**假拆分**——判断两个"完整"的候选是否其实互相依赖到必须合并的地步。

manifest 中 `use_cases[].associations` 恒为空列表；一旦发现代码证据显示两个用例间存在这种依赖关联，正确动作是拆分或合并候选本身，而不是在 `associations` 里登记这段关联——登记关联等于承认了错误的用例边界。

### 对照例：为什么 `Ingest Data` 与 `Query Data`不该合并成 `Manage Data`

用本节判据检验第三节反例表里的过度合并案例：`Query Data` 可以在从未触发过某一次 `Ingest Data` 的情况下对既有数据独立发起并完整返回结果；`Ingest Data` 完成后也不要求紧接着发生一次查询才算"有意义"——两者各自都是独立、完整、对不同时刻的 actor 有价值的使用。它们**不需要连着做**，所以按本节判据应保持两个用例，而不是合并成 `Manage Data`。这与 CRUD 合并（第三节正例最后一行）的区别在于：CRUD 四个操作作用于同一资源的同一生命周期，通常被同一 actor 当作一件事的不同方面来谈论（REQ-N04 的合并前提），而 ingest/query 是两条独立的使用路径，只是恰好共享同一批底层数据。

## 五、`level` 的选择：`user_goal` 与 `subfunction`

- **`user_goal`**：通过第一节完整性判据的候选——独立发起、独立完成、对某个 actor 有可观察价值。这是 29148 A.2.7 场景要求与四类变体覆盖的对象。
- **`subfunction`**：未通过完整性判据、但仍值得单独命名和追溯的可复用片段（典型如被多个 `user_goal` 用例 `includes` 的公共步骤）。它的存在理由是 UML §18.1.3.3 的 include 关系——"公共部分提取为独立用例，被多个 base 用例包含"——而不是独立描述一次完整使用。

**`subfunction` 不强制要求 `scenarios`**：29148 A.2.7 的四类变体覆盖要求（"describes a complete usage"）施加于对 subject 的一次完整使用，`subfunction` 用例按定义不是这样的完整使用，而是某个 `user_goal` 用例内部的片段。对片段本身要求正常/压力/异常/降级四类变体，是把针对完整用例的覆盖要求错误地下放到了子步骤——会制造大量没有独立意义的"场景"，反而助长第二节描述的碎片化失控。`scripts/check_usecase_model.py` 的 `check_29148` 已按此实现：场景变体覆盖检查只对 `level == "user_goal"` 的用例生效。

`subfunction` 用例仍需要 `completeness_check` 之外的其他字段（`name`、`actors`、`evidence`）与 `user_goal` 一样完整——降低的只是场景覆盖要求，不是证据纪律。

### 未通过完整性判据 ≠ 自动升格为 `subfunction` 条目

第一节反例表里"校验权限""`Validate Token`"这类不通过完整性判据的候选，不必然要在 manifest 里单独建一条 `subfunction` 用例——这是 Xpipe 案例过度生成的另一个诱因：把每个不够格的候选都硬塞进模型，只是换了个 `level` 标签，粒度问题原样保留。判断是否值得单列 `subfunction` 条目，用的是 UML §18.1.3.3 的 include 存在理由——**是否被两个或以上 `user_goal` 用例共同依赖，值得作为可复用、可追溯的公共部分单独命名**。只在某一个用例内部出现一次的步骤，直接写进该用例的 `function_details.operation_sequence` 或场景 `steps` 里即可，不必单独建条目。

## 六、三条判据合起来怎么用

实际操作时按顺序对每个候选走完，不要跳步：

1. **完整性判据**（第一节）：这个候选单独看，是不是对 subject 的一次完整使用？否 → 继续判断它是否值得作为 `subfunction` 单列（本节上一条），是则 `level: subfunction`，否则并入调用它的用例正文，到此结束，不再往下走。
2. **关联判据**（第四节）：通过完整性判据、彼此语义相关的候选两两核对——脱离对方单独发起还有没有价值？有，保持独立；没有，合并或改写成 include/extend 关系。
3. **CRUD 惯例**（REQ-N04【二手】）：通过前两条判据、且落在同一资源生命周期上的分立目标（增/查/改/删），按惯例合并命名为 `Manage <X>`；不属于同一资源生命周期的（如 ingest/query），即使表面都在操作"数据"，也不适用这条惯例，维持第二步的结论。

三条判据依次收窄候选集合：完整性判据决定"值不值得存在"，关联判据决定"要不要合并"，CRUD 惯例只是关联判据在资源型操作上的一个特例化命名规则，不能反过来跳过前两条直接套用。

`content-items.md` 末尾自检清单的"每个用例通过完整性判据（执行后可重新发起 / 错误态）"一项，核对的就是本文第一节；产出评审时应逐条能指出每个 `user_goal` 用例的 `completeness_check` 写没写清楚判定理由，而不是只看有没有这个字段。
